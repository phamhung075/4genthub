Decision: remove the two task routes that can only fail, `GET /api/v2/tasks/stats/summary` and `GET /api/tasks/{task_id}`, together with the two adapter methods that panic for them; the statistic 4genthub needs is built by O8 from the ledger, not here

Owner's question, answerable in one line: "The two task endpoints that always return 500: remove them (recommended), keep them failing for Python parity, or build a task-count statistic now?"

Context: board row 6d520676. go-dev found the cause and stopped before changing anything. Measured 2026-10-08 at HEAD:
- `agenthub_go/fastmcp/server/httpapp/task_adapter.go:70-76`: `GetTaskStatistics` and `GetTaskWithRelations` both `panic` with Python's AttributeError text, under the comment "The Python facade has no get_task_statistics / get_task_with_relations". The handlers recover the panic and report a failure, so the route returns 500. This was ported deliberately: `agenthub_go/MIGRATION.md:951` (slice 3: "stats returns 500 ... because the Python facade has no get_task_statistics (AttributeError, preserved)") and `agenthub_go/PROD_READINESS_REPORT.md:179` ("`GET /api/v2/tasks/stats/summary` returns 500 ... in Python too ... these were not bugs"). Both lines cover the stats route only. No parity record mentions `GET /api/tasks/{task_id}` or `get_task_with_relations` apart from the adapter comment.
- Two routes reach these panics, not one:
  - `GET /api/v2/tasks/stats/summary` (`httpapp/task_routes.go:99` → `routes.GetUserTaskStats` → `searchHandler.GetTaskStatistics` → panic).
  - `GET /api/tasks/{task_id}` (`httpapp/routes_mount.go:406` → `routes.GetFullTask` → `searchHandler.GetFullTask` → `GetTaskWithRelations` → panic). The board row names only the first.
- Neither has a caller. In `agenthub-frontend/src` the only mentions are route-list entries in `docs/apiReference.ts` (lines 877 and 109). The task view loads a task through `getFullTask` in `api-lazy.ts:19`, which calls `taskApiV2.getTask`, so it goes to `GET /api/v2/tasks/{id}` → `crudHandler.GetTask` and is not affected.
- The parity reason has expired: `agenthub_main` is archived and being de-linked (NEXT_GEN.md "(1)"), so no Python server is left to match.
- The statistic the product does need is already planned: O8 is a KPI panel (verified tasks per human touch, rework rate, escape rate) "computed by one backend query so the counts agree everywhere", over the O1 ledger.

Options:
- A. Keep parity. The 500s stay, and the routes are documented as deliberately absent. Cost: nothing in code. But two mounted routes are advertised in the route table, the inventory and the frontend's API reference, and they can never answer. That is legacy code kept for a server that no longer runs, which the project's rule forbids.
- B. Build the statistic Python never had: a facade method and a repository query, for example per-user task counts by status, behind the existing route. Cost: a new query, a response shape that nobody has specified, and tests. No caller is waiting for it. It creates a second source of task numbers before O8 builds the first, which is the "counts disagree" failure O8 exists to prevent. It is a build of a feature nobody asked for, not a repair.
- C. Remove both routes and both panicking methods. Cost: a small, behaviour-changing deletion. A caller would now get 404 (route not mounted) instead of 500, and there are no callers. The statistic arrives once, under O8, from the ledger.

Recommendation: C. It is the only option where a route that is listed can also answer. It removes code instead of adding a speculative feature, and it leaves O8 as the one source of task statistics. B becomes right only if the owner names a consumer that needs per-status counts before O8. A becomes right only if Python parity is still a goal, which the archive ruling says it is not.
