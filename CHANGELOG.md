- **Race Condition Fix: Tasks Not Appearing Until Page Refresh** (2025-10-20): Fixed critical bug where tasks created via MCP didn't appear in task list until page refresh, caused by WebSocket animation firing before element registration. **Root Cause**: WebSocket animation service scheduled create animations with 150ms delay, but React component mounting + useEffect registration timing is non-deterministic. Animation fired before TaskRow registered element with AnimationFactory, resulting in "Element not registered" errors. **Analysis**: Traced race condition through complete flow: WebSocket event (150ms delay) → LazyTaskList.addNewTask() → React renders TaskRow → useEffect #1 registers element → useEffect #2 triggers mount animation (50ms). Problem: WebSocket animation at 150ms fires before registration completes. **Solution**: Skip WebSocket animation entirely for 'created' events - mount animation already handles this. Modified WebSocketAnimationService.ts (lines 120-127 for tasks, 192-199 for subtasks) to return early on 'created' action with clear explanation. This eliminates race condition by relying solely on mount-time animation which fires AFTER element registration is guaranteed. **Benefits**: (1) Zero race conditions - mount animation always fires after registration, (2) Cleaner architecture - single animation source for creates, (3) Consistent behavior - tasks/subtasks animate identically, (4) No timing hacks - no guessing optimal delays. **Impact**: Tasks now appear immediately in UI when created via MCP, with smooth animation. Fixes parent issue blocking real-time collaboration features. Files modified: WebSocketAnimationService.ts:120-127,192-199 (skip create animations)

- **Critical Timing Fix: API Fallback Debounce for Sequential Subtask Creation** (2025-10-18): Fixed race condition where API fallback mechanism fetched too early during sequential MCP subtask creation, catching only 2 of 5 subtasks. **Root Cause**: Backend creates subtasks sequentially at ~400-500ms each (5 subtasks = ~2 seconds total). Previous debounce delay of 150ms caused API fetch to execute before all subtasks were created. **Evidence**: Console logs showed `subtasksCount: 2` in API response when 5 subtasks were being created - API query executed at 150ms, catching only subtasks created in first 150ms. **Fix**: Increased UPDATE_DEBOUNCE_DELAY from 150ms to 2500ms in subtaskConstants.ts. This ensures API fallback waits for ALL sequential backend creations to complete before fetching. Debounce timer resets with each new subtask CREATE event, so final API call happens 2.5 seconds after the LAST subtask creation event. **Result**: All 5 subtasks now appear together after brief delay, rather than appearing partially (2 subtasks) then requiring manual refresh. **Trade-off**: Slight delay (~2-3 seconds) before subtasks appear is acceptable since it guarantees complete data. Alternative would be optimistic rendering with WebSocket full payload (backend enhancement needed). Files modified: subtaskConstants.ts:50-53 (LOADING_CONFIG.UPDATE_DEBOUNCE_DELAY: 150 → 2500)

Debug logging added to track optimistic updates in production
