## The 42P08 cast drops its length, so an over-long value is refused by the column instead of being truncated in silence

### Fixed
- **`fastmcp/task_management/infrastructure/repositories/task_event_repository.go`** — the append's `INSERT ... SELECT` now states `$1::varchar` instead of `$1::varchar(64)`. The cast is still on the INSERT SLOT, still alone, and the comparison side and every other statement are untouched; the one token that changes is the length. `6455d4f1` fixed SQLSTATE 42P08 by stating the parameter's type, but a cast to a LENGTHED varchar adds a second effect: PostgreSQL truncates the value to the cast's width before the column is consulted, so an over-length `user_id` is stored cut down instead of being refused. Without the length, both uses of `$1` still resolve to `varchar` (the reviewer's PREPARE probe) and the width is enforced by the column that owns it — silent truncation of an identity is worse than a refusal.

### Testing
- **Both halves measured on the real `task_events` table**, inside the throwaway database `newTestRepoEnv` creates, by a probe that was deleted before this commit: with the 100-character value the reviewer measured, `$2::varchar(64)` **STORED length(user_id) = 64, NO ERROR**, while `$2::varchar` **ERROR: value too long for type character varying(64) (SQLSTATE 22001)**. The evidence therefore shows the truncation AND the refusal, not one of them.
- With `AGENTHUB_TEST_PG_URL` (tools/testpg, port 55432): `TestTaskEventAppendAssignsGaplessSeq` **PASS (0.50s)**, `TestTaskEventAppendRefusesBogusKind` **PASS (0.44s)**, and the whole `./fastmcp/task_management/infrastructure/repositories/` package **ok in 44.540s**. `gofmt -l` on the touched file printed nothing; `go vet` on the package is clean.
- Without the variable the case is a **SKIP, not a pass** — `SKIPPED, NOT PASSED: AGENTHUB_TEST_PG_URL is unset, so this case did NOT run`.
- **No test file accompanies this change, and that is a decision rather than an omission.** Through `Append` the two forms can differ only when a row already exists whose `user_id` is exactly the truncated prefix of the parameter, which needs a synthetic 44-plus-character identity — the unreachable case this row records — so a permanent test would pin a hypothetical rather than a consumer path. The probe is the evidence, and the statement itself is one token.
