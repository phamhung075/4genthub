# `rig send` and `rig whoami` work on a rig the OpenRig daemon hosts

### Changed
- `agenthub_client/internal/clientseat/reseat.go`: `send` accepts the two-argument shape `rig send <session> <text>` — the shape R7 promises and the shape this client's own message deliverer calls — and delivers it through the OpenRig daemon (`POST /api/transport/send`), wrapped in the OpenRig CLI's own `From:`/`To:`/`Sent:` envelope and attributed to `OPENRIG_SESSION_NAME` through `X-OpenRig-Session`. The three-argument `RIG SEAT MESSAGE` shape is unchanged.
- `agenthub_client/internal/clientruntime/command.go`: `whoami` asks the OpenRig daemon (`GET /api/whoami?sessionName=…`, the session from `OPENRIG_SESSION_NAME`) when the shell names a daemon, and prints that document; `--json` prints the daemon's own bytes, which is the shape the OpenRig CLI returns. A shell naming no daemon keeps the native-runtime path unchanged.
- `agenthub_client/internal/clientruntime/openrigdaemon.go` (new): `OpenRigSendMessage` and the pieces both verbs share — the envelope renderer, the base URL (`OPENRIG_URL`, else the loopback address at `OPENRIG_PORT`), the optional `$OPENRIG_HOME/terminal-token` bearer (omitted when absent, as the CLI does), and the identity renderer.
- `agenthub_client/CHANGELOG.md`: the same record, with the tests and the live measurements.

### Why
R7 (`NEXT-GEN2.md` §1.5, lines 141–150, marked delivered) promises a thin `rig` shim that maps `rig whoami`, `rig send`, `rig queue` and `rig ps` onto the client so existing seat prompts and skills work unmodified. On the 4genthub-min rig, which the OpenRig daemon hosts, two of the four refused: `rig send` answered `RIG, SEAT and MESSAGE are required` and its own fallback re-entered that refusal through the binary that IS the shim; `rig whoami --json` exited 3 with `seat identity could not be resolved from active rooms`, because it asked only the native runtime's room store. The client's own fifth safeguard (`sync messages`' deliverer) shells `rig send <session> <text>` and was refused by the same bug.

### Testing
- `internal/clientruntime/openrigdaemon_test.go` and `internal/clientseat/send_test.go` (new): the daemon is asked for the environment's session and receives the sender header; `--json` prints the daemon's document; a 404 becomes the daemon's own reason with exit 3; the envelope is pinned byte for byte (stamp, `· gen <first8>`, the `@external` reply spelling, the `<unknown sender>` label); base-URL and token precedence; two arguments post to `/api/transport/send` and name the session, the daemon's refusal exits non-zero, and one argument never reaches the daemon.
- Live on the 4genthub-min rig. Before (installed shim): `rig whoami --json` → exit 3 `seat identity could not be resolved from active rooms`; `rig send 4genthub-min-fe-dev@4genthub-min "probe"` → exit 2 `4genteam send: RIG, SEAT and MESSAGE are required`. After (binary built from commit `08c41a5` on branch `4genthub-min/r7-shim`): `rig whoami --json` → exit 0 with the daemon's document (identity, four peers, transcript path); `rig send 4genthub-min-reviewer@4genthub-min "R7 SHIM LIVE PROOF …"` → exit 0 `Sent to 4genthub-min-reviewer@4genthub-min`, and the receiver's pane, captured through the daemon, shows `From: 4genthub-min-go-dev@4genthub-min` / `To: 4genthub-min-reviewer@4genthub-min` / `Sent: 10-13 18:56Z · gen 17ec5cb7` / `---` / the text / `---` / `↩ Reply: rig send 4genthub-min-go-dev@4genthub-min "..."`.
- `go build ./...`, `go vet ./...`, `go test ./...` all exit 0 with every package ok; `gofmt -l .` reports only the two pre-existing drifted files (`internal/clientoutbox/commands.go`, `internal/clientwatch/render_test.go`).
- Not run, by instruction: no push, no install, no `rigd` restart, no `4genteam stop`/`up`. The running binary stays pre-fix until the owner builds from this commit.

Both seats can still be reached through the queue; the nudge into their terminals cannot land until those panes recover.
