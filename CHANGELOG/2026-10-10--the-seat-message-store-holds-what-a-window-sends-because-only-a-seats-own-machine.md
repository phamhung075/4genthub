## The seat message store holds what a window sends, because only a seat's own machine can deliver it

### Added

- `agenthub_go/fastmcp/seat_management/infrastructure/schema/seat_management_postgresql.sql` — the **`seat_messages`** table: text a chat window addressed to a seat, held until the client that holds that seat's terminal pulls it. Keyed by the reported names `(user_id, room, seat)` rather than by a seat reference, because no seat table carries a session column at all and a seat that is DOWN is exactly when a message waits. `delivered_at` NULL is what "pending" means; `machine_id` records which machine actually took the message. **This is the first SERVER-authored row on this axis that a CLIENT consumes** — `seat_status`, `seat_feedback` and the session stream are all client-authored — and that inversion is why the row lives here rather than on the session stream, whose `seq` space belongs to the connector's own resume point.
- `agenthub_go/fastmcp/seat_management/infrastructure/database/seat_message_orm.go` — the row struct, the source of truth for the table's columns; `seat_message_orm_test.go` registers it with the DDL-vs-struct map; `seat_tables.go` carries the runtime TableDef. **Both schema creators carry the table**: the SQL file a human applies and the `Tables` registry `createAll` walks, and `TestSeatDDLParity` compares their columns, defaults, references and CHECKs so the two cannot drift apart.
- `agenthub_go/fastmcp/seat_management/domain/repositories/seat_message.go` and `infrastructure/repositories/orm/seat_message_repository.go` — the domain contract and its ORM: `Create`, `ListPending` (oldest first, keyset on `(created_at, id)` rather than an offset, so a message landing mid-page cannot make the walk skip or repeat one), `Ack` (`delivered_at IS NULL` in the WHERE, so a second ack finds nothing and the row keeps the FIRST machine that delivered it), and the two explicit deletes this schema requires wherever CASCADE would otherwise be.
- `agenthub_go/fastmcp/seat_management/application/services/seat_message_service.go` — the store's single writer contract: name validation against the one name rule, a 2000-character bound, the opaque cursor's encoding and decoding, the page's default (50) and hard clamp (200), and **the same credential scan the friction channel runs, from the same `domain/secretscan`** — the chat window is exactly where an operator pastes a token, and a store that kept one would be a leak with a timestamp.
- `agenthub_go/fastmcp/server/httpapp/seat_mount.go` — the two directions of the same path: `GET /api/v2/openrig/rooms/{room}/seats/{seat}/messages` (machine-authenticated, pending messages plus the cursor) and `POST .../messages/{id}/ack` (the delivery record). Both resolve the seat in the room the URL names FIRST, so a seat that is not there answers the SAME 404 as the writer — byte for byte, which the tests assert — rather than an empty page that would read as "nothing is waiting".
- `agenthub_go/internal/clientsync/messagesverb.go` — `agenthub-client sync messages <room> <seat>`, registered in `internal/clientsync/sync.go`. It pulls, types the text into the seat's session with `rig send`, records the delivery in a small local ledger, and ACKs LAST. The order is the contract: an interruption after the typing redelivers (safe), and the ledger removes the one duplicate at-least-once permits, which happens when the text landed but the ACK did not. **The session is not derived from the seat**: no table carries that link, so the verb takes `--session` or the single session `rig ps --json` reports, and refuses when that is ambiguous rather than typing an operator's message into somebody else's prompt.

### Changed

- `POST /api/v2/openrig/rooms/{room}/seats/{seat}/messages` **stores the text instead of refusing it**: it answered 501 with "seat message delivery is not implemented on this server", which was true while nothing held the message, and `seatMessageDeliveryAbsent` is deleted with it. The refusal it replaces stays true in its own words — this server still cannot put text into a seat's terminal — so the message is held and the answer carries the id rather than a claim of delivery.
- `agenthub_go/fastmcp/seat_management/application/services/room_deletion_service.go` — `RemoveSeat` and `DeleteRoom` now delete the seat's or the room's messages **explicitly**, beside their reported statuses: undelivered text addressed to a seat that is going away can never be delivered, and the seat key can be added again from scratch without inheriting the previous inbox.
- `agenthub_go/fastmcp/server/httpapp/seat_mount.go`'s own documentation now STATES THE RESIDUAL LIMIT of the pull rather than leaving it to be discovered: a machine token is bound to a machine and not to seats, so any machine in the tenant can pull any seat's messages in that tenant. That is a chosen limit — binding the pull to the machine that REPORTED the seat refuses it in exactly the case the store exists for, a seat that is down and therefore unreported — and what would narrow it later is a per-seat credential or a seat-to-machine binding the machine reports, neither of which exists today. **The same comment says what that limit IS: a policy choice and NOT a control** — it states the scope rather than enforcing it, nothing in the file stops a machine in the tenant from pulling a seat that is not its own, and the enforcement point is the credential the pull is issued under, so narrowing the rule means changing that credential rather than editing the paragraph. The ack records the machine that actually took each message.

### Testing

From `agenthub_go` with `GOCACHE` and `TMPDIR` inside `.gocache`/`.gotmp`:

- `go build ./...` → exit 0.
- `go vet ./fastmcp/seat_management/... ./fastmcp/server/httpapp/... ./internal/... ./cmd/...` → no output.
- `go test -count=1 ./fastmcp/seat_management/... ./fastmcp/server/httpapp/... ./internal/clientsync/...` → **all ok**: including the DDL parity pair (`database`, which compares the new table's two DDL sources) and `server/httpapp`.
- `go test -count=1 ./fastmcp/seat_management/application/services/...` → ok, with the new `seat_message_service_test.go` and the updated deletion tests (the fake's call list now carries `messages:<room>/<seat>`, and both failure tables have the new call as a failure point).

**What the tests do NOT prove here, stated rather than implied:** this environment has no PostgreSQL (`SEAT_TEST_DATABASE_URL` is unset), so the DB-gated tests skip and the repository's SQL — the keyset page and the `delivered_at IS NULL` update — is not exercised here. The route and service tests prove the ordering, the refusals and the cursor contract against a fake store, and the end-to-end check the row names (a message typed into a real seat's prompt) needs a running seat and a real stack.
