## The documented deploy path resolves against the tree, and its steps match the Go stack

### Fixed
- `.github/workflows/production-deployment.yml`, build job, frontend step: `context: ./agenthub-frontend` with `file: ./agenthub-frontend/Dockerfile.production` named a Dockerfile that does not exist, inside a context that could never contain it. Both move to the repository root — `context: .` and `file: ./docker-system/docker/Dockerfile.frontend.production` — because that Dockerfile `COPY`s `agenthub-frontend/...`, a repository-root-relative path, and the production compose already builds the same image with `context: ../..`. **Changing `file:` alone fails a second time**, which is the trap: `build-push-action` requires the Dockerfile to live INSIDE the context, and a `./agenthub-frontend` context has no `agenthub-frontend/` subdirectory to copy from.
- `deploy-staging` ran on every push to `main` and could only fail: it resolves `docker-compose.staging.yml`, which no compose in this tree provides (the set is backend-frontend, backend-go-frontend, db-only, dev, optimized, pgadmin, production). The job is now dispatch-only (`if: inputs.environment == 'staging'`; the old condition also ran it for a production dispatch, because `github.ref` is the branch dispatched from) and its deploy step refuses with an `::error::` naming the absent file instead of resolving it. Staging's topology is not decided here.
- `scripts/deployment/deploy-production.sh`: seven sites (189, 211, 237, 241, 245, 249, 253) named `docker-system/docker-compose.${ENVIRONMENT}.yml`, missing the `docker` segment; every compose lives in `docker-system/docker/`.
- The same script was still wired to the retired Python stack: `up -d postgres redis` (no compose in this tree defines a `redis` service) and `run --rm backend python -m alembic upgrade head` (the production compose's service is `mcp-backend`, and it is Go). It now starts `postgres`, waits on `pg_isready`, and leaves schema creation to the Go server, which owns it (`AUTO_MIGRATE=true` at `task_management/infrastructure/database/init_database.go`, and the versioned migrations under `agenthub_go/migrations/` after Stage 1).
- `check_prerequisites` required `docker-system/.env.<environment>`, which no compose reads and which does not exist, so the check could never pass; every compose reads the repository-root `.env`. It now requires that file AND asserts the compose file for the environment exists, so a missing definition fails there with a reason instead of surfacing as a `docker-compose` file error halfway through a deployment.

### Tested
- `bash -n scripts/deployment/deploy-production.sh` → `SYNTAX OK`.
- `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/production-deployment.yml'))"` → parses; the frontend step reports `{'context': '.', 'file': './docker-system/docker/Dockerfile.frontend.production'}`, and `deploy-staging.if` reads `inputs.environment == 'staging'`.
- One command per reference: `test -f` resolves all six workflow script paths, both production Dockerfiles, the repository-root `.env` and `docker-system/docker/docker-compose.production.yml`; and the frontend Dockerfile's `COPY` sources (`agenthub-frontend/package.json`, `agenthub-frontend/pnpm-lock.yaml`) exist under the new context.
- The production compose's services, listed with `awk` over the file because `docker` is refused by this seat's policy (not because it is absent): postgres, mcp-backend, frontend, pgadmin, nginx. The script's `up -d postgres` names one of them.
- Leftovers, all zero: `docker-system/docker-compose.` 0, `up -d postgres redis` 0, an executable `run --rm backend` 0 (the one remaining mention is the comment recording the deletion).

### Not in this commit, reported rather than invented
- `tests/performance/load-test.js`, which the `performance-test` job runs with k6, does not exist — nor does `tests/`. A load test needs a target and a shape, so it is a decision, not a missing line.
- The frontend Dockerfile pins `FROM --platform=linux/arm64` in both stages while the workflow builds on `ubuntu-latest` (amd64) with no QEMU setup. That is a fifth fault in the same "the Actions path is red" family and is not a path resolution.
