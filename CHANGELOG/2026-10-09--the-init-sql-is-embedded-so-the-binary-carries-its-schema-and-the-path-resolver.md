## The init SQL is embedded, so the binary carries its schema and the path resolver is gone

### Changed
- `agenthub_go/fastmcp/task_management/infrastructure/database/db_initializer.go` — `//go:embed init_schema_postgresql.sql` supplies the DDL and `ExecuteInitSQLFile` runs **those** bytes; the `filename` parameter and `databaseInitializerSQLFilePath` are deleted outright, with no fallback, no env override and no CWD or `os.Executable` walk. `runtime`, `os` and `path/filepath` leave the file with them. The house mechanism, not a new one: `seedlibrary.go:28` and `blockprovenance.go:59` embed their assets the same way.
- The reason is measured, not argued (row `b231a84b`): under `-trimpath` the old resolver returned the module-relative `agenthub/fastmcp/.../init_schema_postgresql.sql` and read it against the working directory. From a CWD with no `agenthub` component the read failed; from a CWD holding a symlink `agenthub -> agenthub_go` the same binary succeeded; and where `agenthub` is a FILE it failed with not-a-directory, which is the container's shape, since the image's `/agenthub` IS the binary. Nothing in a distroless image makes that path resolve.
- `models_prod.go:3` cited `agenthub_main/src/.../init_schema_postgresql.sql`, which no longer exists — the Go file is the only copy (sha256 `344dc23cf0cbb4b2e95561404387898f1f4b3b46b99d29789fa39ca58f6756e9`) — so the citation now names the embedded file. The `applied_migrations` clause beside it is kept, one line of reason: that table is not in this schema (it is transcribed in `models_prod.go` itself), and "created by the Python migration runner" is provenance for where its DDL came from, which the Go side does not yet replace.

### Verified
- **The container's condition, reproduced locally, now green:** a `-trimpath` test binary run from a scratch directory that holds a FILE named `agenthub` runs the embedded schema — `101 statements to the driver in one transaction`, all three cases PASS. That binary in that directory failed before this change; it is the row's reproduction, re-run as its proof.
- `go test -count=1 ./fastmcp/task_management/infrastructure/database/` → **ok**; `go vet` clean; `gofmt -l` over the package prints nothing; `go build ./...` clean.

### Found while landing this, and deliberately NOT fixed here
- **The inherited chunk rule drops every `CREATE TABLE`.** The file is split on `;` and a chunk starting with `--` or `/*` is skipped WHOLE, so the `-- Table: X` line that precedes each `CREATE TABLE` carries the statement away with it: **75 of 177 chunks are dropped and all 23 `CREATE TABLE` chunks are among them**, while `ALTER TABLE ... ADD CONSTRAINT`, `CREATE INDEX`, `CREATE UNIQUE INDEX` and `DROP TABLE IF EXISTS ... CASCADE` chunks do run. On a real Postgres the run reaches a `CREATE INDEX` on a table it never created and rolls back, so `Initialize` returns false with the reason now logged instead of silently. The new test asserts the two properties this row owes and states plainly that it does not pin coverage either way; the defect is reported to the lead for its own row.
