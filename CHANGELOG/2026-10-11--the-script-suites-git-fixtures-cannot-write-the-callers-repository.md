## The script suite's git fixtures cannot write the caller's repository

Row `qitem-20261011042140-e9cee2248d97c98c`. A defect found by running the suite, fixed at the cause
rather than at the symptom.

### What the leak was

Every fixture under `scripts/tests/` ran git through a local `_git(repo, *args)` helper that passed
`cwd=repo` and **inherited the environment**. Git resolves its repository *before* it looks at the
working directory, so an exported `GIT_DIR` beat `cwd`: `git config user.email` wrote the CALLER's
`.git/config`, `git add` staged into the CALLER's index, and the identity a fixture set for itself landed
outside its own `tmp_path`. The scripts the tests spawn - the hooks under test, `S3-REDERIVE.py`,
`added_line_check.py`, the census instruments - were the second half of the same hole: a child inherits
the parent's environment, so `env=` on the test's own git calls never reached them, and there was no
`env=` there to begin with.

The recorded consequence: a run inside that window put `user.name = scan test` /
`user.email = scan@test.invalid` into this repository's `.git/config`, staged six fixture paths into the
shared index (`NEXT_GEN.md`, `a.txt`, `f.txt`, `g.txt`, `h.txt`, `i.txt`), and fe-dev's `ea3efb20` was
created inside the window and inherited the fixture identity.

### The reproduction

Run first, and against a THROWAWAY NON-BARE `GIT_DIR` rather than the live `.git`: re-injecting the damage
into the live repository would recreate the hazard this row exists to remove, while the mechanism is a
property of `GIT_DIR` being *set*, not of which repository it names.

    GIT_DIR=/tmp/gitdir-repro-25085/.git python3 -m pytest --noconftest -p no:cacheprovider scripts/tests -q

Unfixed, that wrote exactly

    [user]
    	email = scan@test.invalid
    	name = scan test

into that `GIT_DIR`'s config, staged those same six paths into its index, and turned the run from
`88 passed` into `30 failed, 42 passed, 4 skipped` - the collection shrank because the
census cases parametrize over rows they discover through git, which is the same variable the run had
just moved out from under them. The live shared repository was measured before and after that run:
`user.name` and `user.email` still unset, config sha256 `28fe6c39bff326bd54c295bfaeba7a0cfe79ec937a473b519f2cd8a55b6a3b6f`
and index sha256 `13fc2fdce7d271f13a287d3336a162da8be2d5b40be19edcd0986203a65eac71` unchanged.

So the red half of the claim was **another revision's number, not a damaged environment's**: `12 failed,
76 passed` is the SEALED revision `708e3131`'s own clean-tree result, re-verified 2026-10-11 in a detached
worktree with `GIT_DIR` unset, and `7c358c4b` and `5150f16d` - both ancestors of `e0e75084^` - are what

the same command at this branch's tip, on the fixed tree, gives `92 passed`.

### The fix

`scripts/tests/gitfixture.py` is now the only place a fixture gets its git environment:
`environment()` is the caller's environment minus every variable that can relocate a repository
(`GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`,
`GIT_ALTERNATE_OBJECT_DIRECTORIES`, and the whole `GIT_CONFIG*` family - a redirected config is the same
leak with a different target file), and `git(repo, ...)` runs git inside `repo` under it. Every call that
can reach git goes through one of the two: the five `_git` helpers, the `git apply` / `git diff` /
`git check-ignore` / `git worktree add|remove` / `git ls-files` sites that bypassed them, and the six
child processes that run a script which may itself run git. The killer script generated by
`test_git_commit_capture.py` scrubs its own environment, and that file carries an autouse fixture that
removes the relocating variables from the process, because a child the wrapper spawns inherits the
process rather than the call.

Each fixture still sets its identity in its OWN repository (`git(repo, "config", "user.email", ...)`),
which is the point: with the relocating variables gone, `cwd` is the only thing that says which
repository git uses.

### The proof after the fix

    (clean)   python3 -m pytest --noconftest -p no:cacheprovider scripts/tests -q
              -> 90 passed, 3 warnings in 9.72s
    (hostile) GIT_DIR=/home/daihu/__projects__/4genthub/.git python3 -m pytest --noconftest \
                       -p no:cacheprovider scripts/tests -q
              -> 90 passed, 3 warnings in 9.66s

The same verdict under both conditions, and the live shared repository byte-identical across the pair:
`user.name` and `user.email` still unset, `.git/config` sha256
`28fe6c39bff326bd54c295bfaeba7a0cfe79ec937a473b519f2cd8a55b6a3b6f`, `.git/index` sha256
`ee6bdb71547dd064ff0b33db9f2ae46d03a558078e2a6b106d79a20da7247f95`, `git status --porcelain` identical
line for line, `git diff --cached` empty.

`test_git_fixture_is_hermetic.py` keeps it. The behavioural half drives the helper with `GIT_DIR` pointed
at a sentinel repository and asserts the sentinel's config, index and worktree are untouched while the
fixture's own repository still gets a real commit; the structural half parses every test file in the
directory and requires an explicit `env=` on every child that can reach git. Written before the fix, the
structural half named all eleven bypasses by file and line - which is what fails if a fixture written
later opts out.
