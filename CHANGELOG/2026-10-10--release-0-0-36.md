## Release 0.0.36 — the marker moves because the deploys are no longer batched

### Changed
- `agenthub_go/fastmcp/config/version.go` — `ReleaseVersion` **"0.0.35" → "0.0.36"**. That one literal is the
  whole change: `/health` derives its version from it through `httpapp/http.go`
  (`const healthVersion = config.ReleaseVersion`), and the MCP `initialize` serverInfo, the MCP status tool and
  the server records report the same value.

### Why the marker landed mid-batch, against the rule written in the file
- The rule in `version.go` — *"It is the LAST commit in the set before a deploy is requested"* — assumes a
  **manual** push that waits on the owner. It does not hold: `origin/main` equals `HEAD` (`c92350f5`,
  confirmed by `ls-remote`) and commits are being pushed as they land, so a deploy follows within minutes and
  there is no request to be last before.
- Holding the marker under those conditions is worse than moving it: production would keep reporting **0.0.35**
  for a tree that has moved far past it. The lead reversed the earlier hold for that reason, and the reversal is
  recorded here so the next bumper does not re-derive it.
- **Every deploy before this commit is unconfirmable by version**, because the version string did not move with
  the tree. This commit is the first whose presence a `/health` read can prove.

### Verified
- The literal is the only change; `gofmt -l` on the file is clean; `go build ./fastmcp/config/` is rc 0.
- Acceptance is not this commit: `/health` must read **"0.0.36" from a new process**.

### Follow-up: the file's own rule was rewritten the same day
- `version.go`'s doc comment asserted *"It is the LAST commit in the set before a deploy is
  requested"*. That sentence is false under one push regime and true under another, and **which regime
  is intended is the owner's outstanding call**, so the comment now states the **dependency** instead
  of picking one: under a manual, batched push the marker goes last, so it cannot cover a tree that
  lacks the content it names; under push-as-commits-land it goes as soon as the tree holds content
  worth identifying, and a deploy reporting an unchanged version is then confirmable only by
  `/health`'s **uptime**, not by the string. `NEXT_GEN` **rule 80** is cited as the record of what
  happens when the two are confused. The literal did not move in that commit.
