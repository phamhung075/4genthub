## A commit that dies inside the pre-commit stash window can no longer take a seat's uncommitted work with it

### Added
- `scripts/git-hooks/git_commit_capture.py` — the P1 half of row `c029503a`. Before `git commit` runs, it records the worktree's unstaged tracked diff to `<git-dir>/parked-diffs/<stamp>-<seat>/NN-<name>.patch`, **one patch per path**, plus a `MANIFEST.txt` naming each path with its bytes and sha1. `<git-dir>` is the **shared repository**, which is the whole point: the framework parks into the *committing* seat's `$HOME`-derived store, so a victim searching their own cache finds nothing.
- After the commit returns it verifies every captured path: `restored` (the framework put it back), `landed` (this commit carries it — decided from HEAD **moving** and then naming the path), or `at-risk`. On `at-risk` it prints the exact `git apply <patch>` line per path and exits 3, because at that moment the capture is the only copy.
- Retention, stated rather than implied: a run directory is swept only when it is **both** older than `--keep-days` (7) and holds nothing at risk, as recorded by its own verification in the manifest. A capture holding the only copy of anything is never removed — `--list` names it instead. Out of scope on purpose: untracked files, which the framework's window does not touch either.

### Verified
- **A real kill inside the real window, on a scratch repo.** A pre-commit hook that does what the framework does (`git checkout -- .`) and then `kill -9 $PPID` left `f.txt` and `g.txt` back at their committed contents — the parked work gone from the worktree and from the index. The wrapper reported `git commit exited -9`, both paths `at-risk`, and the two `git apply` commands; applying them restored `f.txt` to `one\ntwo` and `g.txt` to `keep\nmore`, and `--list` marks that run AT RISK.
- `python3 -m pytest --noconftest -p no:cacheprovider scripts/tests/test_git_commit_capture.py -q` → **4 passed**; both test files together → **10 passed**.
- Two defects the cases caught before this landed: the AT-RISK block never printed when the commit FAILED (the report was skipped exactly when the verdict mattered most), and `landed` was decided from HEAD's file list alone, which would call a path landed because some *earlier* commit had touched it — while a commit that died inside the window leaves HEAD exactly where it was.
