## O1c landed: the carry step removes `progress_history` WITH CARRY, and the column's Go surface goes with it

### Added
- `agenthub_go/fastmcp/task_management/infrastructure/database/migrations/0003_progress_history_carry_and_drop.sql`: **the step D1 3a rules** (NEXT_GEN's O1c, board row `f9bbdd0f`, item `08739d36`). One file, so the runner holds it in one transaction: it carries every `tasks`/`subtasks.progress_history` entry into `task_events` as a `kind='progress'` event with the content byte-for-byte, the entry's own timestamp, its `progress_number` and `carried_from`; it **checks** the carry (every stored entry must have a ledger twin under the identity the reader merges on - content plus progress_number - and a number held by a *different* content raises, because that is a collision rather than a match); and only then drops `progress_history` and `progress_count` on both tables. A failed step records no `applied_migrations` row and leaves the column intact.
  - A **malformed entry fails the step where `0002` skips it** - an entry with no content, no number or no timestamp raises. `0002` could skip them because it destroyed nothing; this step is about to destroy the source, so a note it cannot read must stop it (`NEXT_GEN.md`'s O1c check: "a malformed entry -> step fails, column intact").
  - It takes each affected user's advisory lock in the same key `TaskEventRepository.AppendInTx` uses, because the runner's own lock is a different key and the MAX+1 numbering could otherwise race a live append.
  - `0002_progress_notes_backfill.sql` stays and is untouched: it is the additive bridge, and an applied step's name is its identity.
- `agenthub_go/fastmcp/task_management/infrastructure/database/progress_history_drop_integration_test.go`: the step's acceptance against a real PostgreSQL, three cases. It carries the notes and drops the columns (asserting the ledger's payload and the catalogue); it **fails** on a malformed entry and leaves the column, the note and the ledger row intact; and it does not carry a note the ledger already holds twice. The boot applies the embedded set, so each case recreates the pre-drop columns first - the schema the step exists to meet.

### Changed
- **The column's Go surface is gone**, so the ORM, the entities and the repositories agree that progress is the ledger: `models.go`'s task/subtask fields and the four registry rows; `domain/entities/task.go`'s two fields, their nil-init, `ProgressEntries`, `GetProgressHistoryText`, the `progress_history` domain event, and the column writes in `AppendProgress`; `domain/entities/subtask.go`'s two fields and its whole `AppendProgress` (its only job was the column, and D1 3a says the subtask dialog shows no progress section until `06410692` is re-landed over the ledger); the row-to-entity and entity-to-model mappings in `task_repository.go` and `subtask_repository.go`; and - the path `2c4582de` introduced - `repoPlainValue`, `taskRepoDecodeHistory` and `subtaskRepoDecodeHistory` with them.
- `Task.AppendProgress(number int, content string)`: the note is still built for the recorder, but **the number is the caller's**, and `application/use_cases/status_ledger.go` gains `NextProgressNumber` - one past the highest `progress_number` the task's `progress` events carry. The number must come from the ledger because the carry copies the column's numbers in intact: a task whose notes were numbered 1..N must continue at N+1, and a restart at 1 would collide on the identity the merge and the carry's guard both use, silently losing the note. `create_task.go` and `update_task.go` pass it; `update_subtask.go`'s progress call is dropped.
- `application/services/websocket_payload_builder.go`: the entity branch has no progress source left, so its `details` is `""`; `includeProgressHistory` still gates the response branch, which is built with the events.
- `init_schema_postgresql.sql` and `models.go`'s literal `CREATE TABLE` DDL **keep** the two columns: `0002` references them unconditionally and runs after `createAll`, so a schema built without them makes `0002` fail at plan time and takes the whole boot with it. The DDL declares the pre-step state and `0003` removes it - which is what an incremental migration looks like, and the columns come out of the DDL for good when T12's `0001` baseline fold lands, a separate step.

### Verified
- **The step on a real pre-packet database, by hand.** Booted the OLD binary (`origin/main` `3e07f781`) with `AUTO_MIGRATE=true` over a scratch database, seeded a task note and a subtask note **in the column**, then ran the step's SQL in one transaction: it committed, both notes are in the ledger with their numbers, timestamps and `carried_from`, and all four columns are gone.
- **The two-binary upgrade gate (`ai_docs/verification/schema-upgrade-gate.md`), which this packet requires.** Same procedure on a fresh scratch database: the old binary built the pre-packet schema (four columns present), the **new** binary booted on it and left `applied_migrations` = [`0002_progress_notes_backfill`, `0003_progress_history_carry_and_drop`], **NONE** of the four columns, and the ledger holding both carried notes; a **second** boot of the new binary re-ran the set and left the ledger at exactly 2 events - the carry did not double. **Stated precisely:** that second process ended on `listen tcp 0.0.0.0:8124: bind: address already in use` because the first boot was still listening - my harness's bookkeeping, not the server's - so the *migration* outcome above is what is measured, and "the second process stayed up" is not claimed. Both scratch databases were then DROPPED, per the gate's rule that a scratch database left migrated makes the next run pass vacuously.
- `gofmt -l` empty on the touched files; `go build ./...` rc 0; `go vet ./...` rc 0; `go test -count=1 ./fastmcp/task_management/infrastructure/database/` -> **ok 16.812s**; `./fastmcp/task_management/infrastructure/repositories/` -> **ok 142.358s**; `domain/entities/` -> **ok**; `application/dtos/task/`, `application/services/`, `domain/services/`, `server/mcptoolpath/progressdetails/` -> **ok**. The package whose cases pinned the column (`TestEveryTableDefColumnHasAPath`, `TestSchemaValidatorRealPostgres`, `TestAcceptanceScopeEnsurerRestoresAnOldShapeWithRows`, the two `0002` carry cases) is green after the change.
- **Two failures found by that run and fixed rather than papered over**: `ProgressTextWith` was already filtering non-`progress` events correctly, and the failing assertion was a stale expectation in `task_test.go` that compared a two-note render against a one-note input; and this packet's own new test read a JSON object with `->> ` twice (`text ->> unknown`), which is a type error rather than a wrong answer.
- `TestProgressDetailsRoundTripThroughTheTools` (`server/mcptoolpath/progressdetails/`) is the wire test the ruling keeps: it now asserts the ledger's shape - exactly one `progress` event per note - instead of reading the column, and it passes.
