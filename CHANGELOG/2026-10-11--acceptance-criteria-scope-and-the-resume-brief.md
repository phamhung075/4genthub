## Acceptance criteria, scope, and the resume brief

### Added
- **Two columns on `tasks` and `subtasks`**: `acceptance_criteria` (a JSONB string array) and `scope` (a JSONB glob array), settable through `manage_task` and `manage_subtask` on both create and update. A JSONB column on these tables spans six places and all six are here: the entity fields, the database row structs with their `db` tags, the TableDef `ColumnDef` and its DDL, the embedded `init_schema_postgresql.sql`, the repository conversion both ways, and - the one an EXISTING database actually takes, since `migrations/` holds only a README - a registered **ColumnEnsurer** (`acceptance_scope_ensurer.go`). Both are `NOT NULL DEFAULT '[]'`, so a database that is migrated and a database that is created agree.
- **`manage_task action=resume`**, returning ONE brief built from the task, its subtasks, its context and the ledger: `application/services/task_resume_service.go`. Its sections are emitted in the order that is also the priority the lead decided: `task`, `acceptance_criteria`, `last_verdict`, `next_action`, `open_subtasks`, `blockers`, `last_evidence`, `context`, `last_handover`, `budget`. The rationale, so the shape is reviewable rather than habitual: the brief's consumer is a resume, and a resume that cannot name the criteria, the last rejection's reasons and the next action in its first three sections has failed whatever its length.
- **The size budget** is `resumeBriefTokenBudget = 4000`, ONE named constant using `contextpacks.EstimateTokensOf` over the brief's own JSON, marked in the code as a PRODUCT DEFAULT the owner may change without any shape moving. The brief is **never truncated**: `budget.tokens`, `budget.limit` and `budget.overage` are always reported, and the over-limit case returns the whole brief with a positive overage. The section order is what a future reduction policy would cut against; it is not a licence to cut now.
- **Evidence is inlined as FACTS and linked as BULK**: the two shas, the failing test NAMES and the touched-file count, with the raw `numstat` - the one unbounded part - reachable through the events route rather than inlined. That is how a 4000-token budget stays honest without a silent cut.
- **The next action** is a deterministic ladder over the facts, most recent blocking fact first: a REJECT gate verdict -> `fix: <its reasons>`; else a failing evidence run -> `fix: <the failing names>`; else open subtasks -> `continue: <n> open subtask(s)`; else a not-done dependency -> `blocked: <ids>`; else no evidence at all -> `start: submit evidence with 4genteam evidence`; else `continue`.

### The two-caller property is STRUCTURAL, not asserted
The box asks that the brief be identical for two different callers. The service makes that true by construction rather than by comparing two runs: **the ledger seam it defines (`TaskResumeEventRead`) takes NO caller parameter at all** - the seat-scoped repository instance supplies the isolation - and nothing in the brief is built from an identity, a seat, a session or a clock. A test also compares two callers byte for byte, and it is worth having; but the reason it passes is the signature, and a signature cannot drift the way an assertion can.

### Not done, named rather than implied
- Out of scope for this box and not stubbed: the GATE that writes `gate_verdict` events (O5). Nothing in the tree writes one yet, which is why the REJECT case SEEDS that event through the ledger's one writer instead of pretending a gate ran.
- `context` in the brief is the TASK-LEVEL context document, which is what that level holds. Inheritance resolution across levels exists as `manage_context action=resolve` and is not re-implemented here.
